## Executive summary

Project #240 remains the operational tracker for the [`WordPress/ai`](https://github.com/WordPress/ai) Showcase Plugin (288 of 290 cards; the others are Google-provider issue #23 and `php-ai-client#242`). The plugin continues to organize user-facing AI capabilities as toggleable experiments over shared Connectors, AI Client, Abilities API, MCP, and request-log infrastructure.

**The board shrank for the first time since 2026-08-01: 291 → 290** = 228 PRs + **62** issues, Done **218 → 216**, non-Done **73 → 74**. Three cards in, one PR to Done, and **four already-Done issue cards de-carded**. Every diff category that describes *existing* cards is empty: zero status moves, zero milestone moves. Nothing on this board changed its mind this window; cards only arrived, finished, or were deleted.

**The de-carding pass reached into the release that just shipped.** [#233](https://github.com/WordPress/ai/issues/233), [#307](https://github.com/WordPress/ai/issues/307), [#690](https://github.com/WordPress/ai/issues/690), and [#876](https://github.com/WordPress/ai/issues/876) left the board — all closed on **2026-08-10/11**, all Done, and **three of the four carried milestone 1.3.0**. So the 1.3.0 board lane, which closed at 19/19 on release night, now shows **16 cards** eight days later, against a repository milestone still closed at **71 items**. The board is not a durable record of what a release contained, and this is the seventh cleanup pass to demonstrate it. (#307 is also the `NOT_PLANNED` AGENTS.md decline — a proposal that was refused, counted as Done, and has now been erased.)

**The embedding programme restarted exactly as #962 asked — and the board cannot see any of it.** Tracking issue [**#962**](https://github.com/WordPress/ai/issues/962) said in plain terms that #683/#891/#943 "should be divided into smaller, independently reviewable PRs." Two such PRs arrived this window: [**#975**](https://github.com/WordPress/ai/pull/975) (dkotter, +1,144/−292 across 19 files, milestone 1.4.0, `[Status] Blocked`) brings the latest embedding code over from `php-ai-client#274`, re-enables `SDK_Overlay`, and re-adds a temporary `wp ai embeddings generate` WP-CLI command for testing; [**#976**](https://github.com/WordPress/ai/pull/976) (ColinM-sys, +2,027/−1 across 11 files, 51 tests, 93% patch coverage) is the **storage and CRUD layer** — a portable `wpai_embeddings` table whose unique key is `(object_type, object_id, provider, model, chunk_index)`, so an index can never be queried with vectors from a different model. **Neither is carded. Neither carries a closing reference** — both say "Part of #962" / "See #962" — so both land as `unexplained`, and #962's own checklist is still seven unchecked boxes with no PR links. The decomposition the board asked for is happening in a place the board does not record.

**The gate opened.** [`php-ai-client#274`](https://github.com/WordPress/php-ai-client/pull/274) — the required-model change that has blocked the plugin's embedding substrate since #946 switched it off on 2026-08-17 — was **APPROVED by JasonTheAdams on 2026-08-25 at 22:23 UTC** and is now **CLEAN**, after a `CHANGES_REQUESTED` round on 2026-08-24 and three response commits. It is still unmerged. dkotter opened #975 at **20:52 — ninety minutes before the approval landed** — betting on it.

Every approval this window went to a PR that merged within hours of receiving it, while the standing 33 open PRs recorded **zero** — a **twelfth** consecutive window at zero.

**The same-day issue→card→Done→uncarded-PR loop ran again, faster.** [**#968**](https://github.com/WordPress/ai/issues/968) (hbhalodia) reported that `Uninstall.php`'s `delete_meta()` doc comment claims to delete post/comment/term meta while only deleting user meta. **A third governance track opened, and it names an existing blocker.** [**#971**](https://github.com/WordPress/ai/issues/971) (WouterP0lman, 2026-08-25, Triage, unmilestoned) is an RFC for an **AI Governance experiment** — role-based access to AI, per-period usage limits, per-user/feature attribution, and defined behavior at the limit — explicitly local and site-owned, with no hosted service or telemetry. It reports a working local proof of concept *and* the reason that PoC is not being proposed: its enforcement path used `pre_http_request`, which cannot identify the client, actor, feature, or model. So it names [**#732**](https://github.com/WordPress/ai/issues/732) — AI Request Logging misses providers with sidecar transports — as a prerequisite, and asks that #732's lifecycle direction be settled before enforcement is built. **The board now carries three overlapping governance threads**: identity (#923, In discussion, implemented uncarded in #961), access control (#736, In progress, PR #749 CHANGES_REQUESTED), and usage governance (#971, Triage) — and the newest one is the only one that states its dependency.

**Upstream moved more than the plugin did.** `WordPress/php-ai-client` went 32 → **31** PRs with **two merges** — **#231** (skip live model-list fetches for explicit text model IDs, closing #230) and **#275** (provider-plugin version bumps), both merged by jeffpaul on 2026-08-24, the first merges there in three windows — and gained draft **#282** (superdav42) implementing new issue **#281**, *provider-agnostic deferred tool loading*: mark declarations deferred, let the model discover and load them, and stop sending a whole ability catalog on every request. That is a direct upstream answer to the board's oldest open question, **#21** ("how to best support hundreds or thousands of abilities"). `WordPress/mcp-adapter` jumped 13 → **17** — justlevine opened three CI/tooling PRs (#302, #303, #304) inside three hours on 2026-08-26, plus **#299** (shoemoney: `resources/read` returns a 500 for any ability with an object input schema, `Fixes #261`) and draft **#300** (SSE streaming on the HTTP GET transport) — while dependabot **#296** was closed unmerged and **#288** (deprecate the bundled-dependency path) picked up justlevine's approval. `WordPress/abilities-api` is **static on every axis for a fifth consecutive census** at 14 / 8 / v0.4.0, still pending archival. The dependency watchlist holds at **16 (9 open / 4 closed / 3 merged)** with **zero drift on every axis for a second consecutive window** — not even an activity bump.

The forward roadmap still converges on four bets: (A) Abilities as the universal tool layer — where #961 still puts uncarded code against #923, #945's `core/edit-content` waits carded and unapproved, and `php-ai-client#281` now offers a scaling answer to #21; (B) a provider-agnostic Connectors ecosystem, where #933 (PR #935) remains the review-ready fix nobody has approved; (C) an editorial lifecycle that shipped translation, slugs, and abilities gating in 1.3.0 and is now taking small fixes at speed (#967, #972, #977) while its larger items (#949 Knowledge/Guidelines, #951 block labels) sit still; and (D) conversational/site-agent and semantic-search surfaces, where the substrate finally has an approved upstream gate and two decomposed PRs — neither of which the board can see. The delivery lane is **v1.4.0 (24 non-Done, no release issue, no date)**; **Future Release holds 42**; **v1.5.0 is still an empty milestone**.

## 3. Product architecture

The mental model that explains every item on the board:

**Experiments (user-facing, toggleable AI features):**
Title Generation · Excerpt Generation · Alt Text Generation · Image Generation · Content Summarization · Content Classification · Content Resizing · Comment Moderation · "Refine"/Editorial Updates (Notes) · Abilities Explorer

**Shared infrastructure:**
- **Connectors** — the screen where AI **provider plugins** register (Anthropic / Google / OpenAI by default).
- **Abilities API** (WP core) — the tool/capability layer; **the strategic keystone** (maps to MCP, WebMCP, Skills, Command Palette).
- **WP AI Client** (WP 7.0 core) — the in-core prompt/model client features call.
- **AI Request Logs** — observability (the dominant recent theme).
- **MCP** adapters — expose abilities to external agents.
- ~~**`AI_Service`** layer~~ — **deprecated, and the card is closed.** Introduced in 0.2.1 (#101) as shared internal routing that experiments would migrate onto (#233), it was never adopted. PR [#905](https://github.com/WordPress/ai/pull/905) **merged 2026-08-11**: the class and the `get_ai_service()` helper stay, marked deprecated, after dkotter noted both are public surface a third party could be calling. **#233 closed against it**, closing out the "board contradicted by its own implementation" case — and **#233 was de-carded from the board this window**, so the board no longer records that the refactor was ever planned. All experiments call `wp_ai_client_prompt()` directly.

Every roadmap item is a **new Experiment**, an **enhancement to one**, or **infrastructure/governance** beneath them.

## 6. Planned roadmap — strategic bets

Four converging directions. Most sit in **"Future Release"** (uncommitted) unless noted.

### A. Abilities API as the universal tool layer → Platform & Standards

## 8. Strategic read & risks

**Where it is heading:** discrete AI helpers are becoming a governed, agent-capable WordPress platform. Abilities provide the action primitive; Connectors and model preferences provide provider independence; editorial experiments provide user-facing workflows; search/RAG, MCP/WebMCP, and site-agent ideas connect those layers. v1.3.0 is the first release to ship a *gate* alongside the capabilities — the Custom Abilities toggle — which is the platform thesis arriving in a user-visible form.

## 10. How to refresh this document

> ⚙️ **Automated path:** [`wp-ai-roadmap-refresh.sh`](./wp-ai-roadmap-refresh.sh) does everything below in one command — re-pulls the board, diffs against the last snapshot (added / newly-Done / merged / status & milestone moves / removed), fetches the full PR/release census for all repositories declared through [`wp-ai-roadmap-repositories.json`](./wp-ai-roadmap-repositories.json), refreshes the curated dependency watchlist, and can append a changelog row (`--update-changelog`). Run with no args for a read-only report; add `--save` to roll all board, repository, release, and dependency baselines forward. The manual recipe below is what it automates.
>
> **Normal vs. strict refresh.** The default (normal) refresh is *warning-only*: any data-quality or coverage problem — an unreachable dependency, a substantive open PR with no board representation — is reported in the output (`.validation` in JSON, stderr lines otherwise) but never blocks the board report, and the run exits `0`. `./wp-ai-roadmap-refresh.sh --strict [--json]` runs the same read-only pipeline as an **audit**: it emits the complete report first, then exits `2` when any validation error remains (exit `1` is reserved for operational failures that prevented a report at all). A strict failure also suppresses `--save` and `--update-changelog` ("persistence skipped"), so a red audit never rolls the baseline forward.
>
> Strict is a **scheduled visibility audit, not a merge gate**: whether every substantive `WordPress/ai` PR is linked to Project #240 depends on upstream contributor behavior, so a persistent red result means *unresolved roadmap visibility* (work in flight that the board doesn't show), not a broken tracker. Point-in-time coverage: **33 open PRs** = 17 direct board PR cards + 12 linked to board issues (**all 12 via authoritative `closing` references**) + 0 routine dependency PRs + 0 linked-off-board + **4 unexplained (#961, #975, #976, #977)**. Exactly one fallback-parsed relationship remains anywhere in the census: #494 → #238, on a direct board PR card. **Read that number with its blind spot in view.** It counts only PRs that are still open, so it rises and falls with queue throughput rather than with tracking discipline: last window it hit 1-of-30 partly because nine uncarded PRs *merged*, and this window it fell to 4-of-33 because three substantive PRs simply opened. The stable measure is milestone-level — the repository's `1.4.0` milestone holds **47 items**, the board cards **29**, and **nine of the 18 uncarded are already merged**. The issue-side audit has no such gap — every open `WordPress/ai` issue is checked against the board on every run (**54 of 54 carded**).
>
> **Cold-query caveat, now handled by the script.** GitHub computes PR mergeability lazily, so a first census can answer `mergeStateStatus: "UNKNOWN"` for PRs nothing has touched — the 2026-08-10 run reported 27 of 36 that way. `fetch_pr_census()` now re-asks once and keeps whichever answer knows more, warns (`pr-mergestate-unknown`, never an error) if any PR stays cold, and the PR diff ignores transitions into or out of `UNKNOWN`. Without that, one cold run reports every open PR as newly unreadable *and* persists the sentinel into the baseline, so the next window reports them all again in reverse.

**Prerequisite:** a `gh` login whose token has the `read:project` scope (fine-grained PATs scoped to a personal account **cannot** read the WordPress org project — even though it's public; use a classic-token login):

```bash
gh auth refresh -h github.com -s read:project
```

**1. Pull the full board** (paginated GraphQL → raw JSON). Save this query as `proj240.graphql`:

```graphql
query($org: String!, $number: Int!, $endCursor: String) {
  organization(login: $org) {
    projectV2(number: $number) {
      title shortDescription url
      items(first: 100, after: $endCursor) {
        totalCount pageInfo { hasNextPage endCursor }
        nodes {
          type
          fieldValues(first: 25) { nodes { __typename
            ... on ProjectV2ItemFieldSingleSelectValue { name field { ... on ProjectV2FieldCommon { name } } }
            ... on ProjectV2ItemFieldTextValue   { text field { ... on ProjectV2FieldCommon { name } } }
            ... on ProjectV2ItemFieldDateValue   { date field { ... on ProjectV2FieldCommon { name } } }
            ... on ProjectV2ItemFieldNumberValue { number field { ... on ProjectV2FieldCommon { name } } }
            ... on ProjectV2ItemFieldIterationValue { title startDate field { ... on ProjectV2FieldCommon { name } } } } }
          content { __typename
            ... on Issue { number title url state stateReason repository { nameWithOwner }
              labels(first:20){nodes{name}} assignees(first:10){nodes{login}} milestone{title}
              createdAt updatedAt closedAt comments{totalCount} }
            ... on PullRequest { number title url state isDraft repository { nameWithOwner }
              labels(first:20){nodes{name}} assignees(first:10){nodes{login}} milestone{title}
              createdAt updatedAt closedAt mergedAt }
            ... on DraftIssue { title assignees(first:10){nodes{login}} } } } } } } }
```

```bash
gh api graphql --paginate -f query="$(cat proj240.graphql)" -F org=WordPress -F number=240 > proj240_raw.json
```

**2. Normalize to flat items** (flattens custom fields into a `fields` object):

```bash
jq -s '[ .[].data.organization.projectV2.items.nodes[] ] | map({
  type:.type, itype:.content.__typename, number:.content.number, title:.content.title,
  url:.content.url, repo:.content.repository.nameWithOwner, state:.content.state,
  mergedAt:.content.mergedAt, milestone:.content.milestone.title,
  labels:[.content.labels.nodes[]?.name], assignees:[.content.assignees.nodes[]?.login],
  fields:( [ .fieldValues.nodes[] | select(.field.name!=null) |
    {key:.field.name, value:(.text // .name // (.date|tostring) // (.number|tostring) // .title)} ] | from_entries ) })' \
  proj240_raw.json > proj240_items.json
```

**3. Re-derive the key views:**

```bash
# Status distribution
jq -r 'group_by(.fields.Status)[] | "\(length)\t\(.[0].fields.Status)"' proj240_items.json
# All open issues (the roadmap), by status + milestone
jq -r '[.[]|select(.itype=="Issue" and .fields.Status!="Done")] | sort_by(.fields.Status,(.number)) | .[] |
  "[\(.fields.Status)] \(.milestone//"—") #\(.number) \(.title)"' proj240_items.json
# Milestone × Done/Open
jq -r 'group_by(.milestone)[] | "\(.[0].milestone//"(none)")\tTot:\(length)\tDone:\([.[]|select(.fields.Status=="Done")]|length)"' proj240_items.json
```
