## Executive summary

Project #240 remains the operational tracker for the [`WordPress/ai`](https://github.com/WordPress/ai) Showcase Plugin (289 of 291 cards; the others are Google-provider issue #23 and, new this window, `php-ai-client#242`). The plugin continues to organize user-facing AI capabilities as toggleable experiments over shared Connectors, AI Client, Abilities API, MCP, and request-log infrastructure.

**v1.3.0 shipped.** The release that the last two windows recorded as overdue was tagged on **2026-08-18 at 21:04 UTC** — one day past its 2026-08-17 target, **35 days after v1.2.0** — the longest gap since the 0.1.1 → 0.2.0 alpha stretch, against a cadence that had been roughly two weeks. jeffpaul ran the full checklist inside three hours: release PR [#958](https://github.com/WordPress/ai/pull/958) merged 20:19, plugin check and tests green 20:56, local testing 21:00, GitHub release 21:04, WordPress.org deploy 21:11, [announcement post](https://make.wordpress.org/ai/2026/08/18/whats-new-in-ai-1-3-0/) 22:32. The 1.3.0 milestone closed at **71 items**, release issue **#924** closed, and the 1.5.0 milestone was created empty at 19:46 the same evening.

**It closed at 19/19 Done because the one thing that was not finished was moved out.** C2PA detection **#421** — the release's last substantive item — went **1.3.0 → 1.4.0**, so the lane emptied by deferral rather than by delivery. Its PR **#459** did the opposite of what the board expected: its checks went **FAILURE → SUCCESS** for the first time in weeks, arriving green in the same window it was descoped.

**The board grew after two flat windows: 279 → 291** = 228 PRs + 63 issues, Done **214 → 218**, non-Done **65 → 73**. Fourteen cards added, two removed, three newly Done, three status moves, three milestone moves. But the growth is intake, not throughput: **eleven of the fourteen additions are new issues or PRs filed during the window**, and the Done column moved by exactly three.

**⚠️ The carding gap did not close — it moved from the open queue to the merge stream. Thirteen PRs merged this window and nine of them never had a board card.** Carded: #917, #941, #948, #960. Uncarded: **#947** (Done'd #940 — see below), **#950** (content sanitization), **#952** (IPv4-in-IPv6 check for PHP <8.3), **#958** (**the 1.3.0 release PR itself**, 62 files), **#959** (CREDITS), and dependabot **#963/#964/#965/#966**. Four of those shipped *in* v1.3.0. The open-PR audit reads better than ever — **1 unexplained of 30** — precisely because the uncarded work merged. Point-in-time PR coverage measures what is still waiting; it cannot see what arrived and left, and this window it could not see the release.

**One Done card is Done against a PR the board never saw, for a fix it did not ask for.** Issue **#940** asked for a *custom settings endpoint* to bypass core's `/wp/v2/settings` key-revalidation bug. It closed on 2026-08-19 against uncarded PR **#947** (hbhalodia), which **raises the HTTP timeout** for `wp/v2/settings` PUT/POST instead — a different remedy for the same symptom, authoritatively `Closes #940`. The board recorded the closure, gave the card milestone 1.4.0, and has no representation of the PR, the change, or the fact that the requested endpoint was not built.

**The reversal from last window got a tracker, and it is the most consequential board-new card.** [**#962** "Tracking: Implement Embedding Support"](https://github.com/WordPress/ai/issues/962) (jeffpaul, 2026-08-20, In progress / 1.4.0, **assigned dkotter**) decomposes the embedding programme into seven independently reviewable steps and states the lesson explicitly: existing work (#683, #891, #943) "should be divided into smaller, independently reviewable PRs rather than combining foundational architecture and user-facing features into large feature PRs." dkotter confirmed on the thread that re-enabling what #946 disabled waits on `php-ai-client#274`. ColinM-sys then tested **#274 end-to-end against a local Ollama** (unit suite green on PHP 7.4–8.5, 36/36 live cases) and surfaced a concrete migration cost: #274 removes `usingProvider()`/`usingModelPreference()` from `EmbeddingBuilder`, both of which `generate_embeddings()` calls and both of which #891/#943 depend on. **The board also gained `php-ai-client#242` as a card** — In progress under 1.4.0, though that upstream issue closed on 2026-07-15. It is the second hygiene straggler alongside merged-but-Needs-review #484, and the first non-Done card in another repository's closed state.

**Coverage of open PRs is at its best reading in months, and the one failure is a governance PR.** The closing census reads **30 open PRs = 18 direct + 11 linked + 0 routine + 0 off-board + 1 unexplained**, all 11 links authoritative `closing` references, and **52 of 52 open issues carded**. The single strict-audit failure is **#961** (gziolo, +2,439/11 files, `[Type] Proof of Concept`): "Add Agent Users, dedicated accounts for AI agents" — the implementation of the identity half of **#923**, which it references without a closing link. So the board's most substantive open governance discussion now has code against it that the board cannot see, while #923 itself sits In discussion under Future Release. Last window's other two failures resolved by being carded (#943, #945) or merging (#941).

**Review throughput moved for the first time in months — and still not for the standing queue.** Thirteen merges, every one merged by a maintainer (dkotter 11, jeffpaul 2 — both his own). Two were contributor PRs that had been waiting: **#917** (Infinite-Null, open 15 days) and **#941** (yogeshbhutkar, open 7 days). The other eleven were maintainer, release, or dependabot work that mostly opened and merged inside the same window. But the standing queue is unchanged: **0 of 30 open PRs carry an approving review**, an eleventh consecutive window at zero, with **19 BLOCKED / 11 DIRTY**, **17 failing checks**, 10 CHANGES_REQUESTED, and 7 drafts. Readiness moved in both directions this time rather than only backwards — #459 and #749 went green on checks; #887 and #888 went DIRTY → BLOCKED, #887's checks SUCCESS → FAILURE. On the window's closing day **#929 left draft** (zeus2611, +2,907 lines across 27 files, checks already green): the largest contributor PR in the repository asked for review at 14:48 UTC and joined a queue that has approved nothing in eleven windows.

**Triage nearly tripled on one experiment's follow-ups.** lnispel filed five unmilestoned C2PA Monitor issues (**#953**–**#957**) on 2026-08-18, all follow-ups to PR #459: JUMBF/CBOR decoding, in-browser verification via `@contentauth/sdk`, a grid-view indicator (blocked on the C2PA Conformance Program — WordPress cannot use the CR trustmark), manifest preservation through the GD/Imagick subsize pipeline, and CAI Verify pre-fill. Triage went **3 → 8**, and the C2PA read path now has more open follow-up issues than the experiment has merged code.

**Upstream: the gate held, and one repository got quieter by resolving rather than merging.** `WordPress/php-ai-client` went 29 → **32** PRs / 34 → **35** issues; all three new PRs are zahidgh's (**#278** adapter docs, **#279** nullable token usage closing #158, **#280** a provider hook for function declarations), and new issue **#277** reports that `MessagePart` cannot carry citations, so every provider silently drops source attribution. **#274 is still open, still BLOCKED, still `REVIEW_REQUIRED`, and still the single gate on re-enabling the plugin's embedding layer** — open since 2026-08-13, and the gate since #946 merged on 2026-08-17. `WordPress/mcp-adapter` went 14 → **13** (#291 merged, #292 closed as a duplicate) with issues 41 → **43**: **#297** (unknown `mcp.type` values coerce to `tool` — fails open) and **#298** (`create_error_result()` discards `WP_Error`'s code and data). `WordPress/abilities-api` is static at 14 / 8 / v0.4.0 — unchanged on every axis across all four snapshots since it entered the census on 2026-08-10 — still pending archival. The dependency watchlist holds at 16 (9 open / 4 closed / 3 merged) with **zero drift on every axis** — no membership, state, milestone, title, or activity change.

The forward roadmap still converges on four bets: (A) Abilities as the universal tool layer — where #961 now puts uncarded code against the agent-identity question #923 opened, alongside carded #945's `core/edit-content` write ability; (B) a provider-agnostic Connectors ecosystem, where #933 (PR #935) is the live defect and #940's core-revalidation bug was fixed uncarded by #947; (C) an editorial lifecycle that just shipped translation, slugs, and abilities gating in 1.3.0 and is now loading block labels (#951) and Knowledge/Guidelines (#949); and (D) conversational/site-agent and semantic-search surfaces, still the most crowded and least settled — three PRs, a tracking issue, and an embedding layer that remains switched off. The delivery lane is **v1.4.0 (24 non-Done, no release issue yet)**; **Future Release holds 42**, and **v1.5.0 is an empty milestone waiting for scope**.

## 3. Product architecture

The mental model that explains every item on the board:

**Experiments (user-facing, toggleable AI features):**
Title Generation · Excerpt Generation · Alt Text Generation · Image Generation · Content Summarization · Content Classification · Content Resizing · Comment Moderation · "Refine"/Editorial Updates (Notes) · Abilities Explorer

**Shared infrastructure:**
- **Connectors** — the screen where AI **provider plugins** register (Anthropic / Google / OpenAI by default).
- **Abilities API** (WP core) — the tool/capability layer; **the strategic keystone** (maps to MCP, WebMCP, Skills, Command Palette).
- **WP AI Client** (WP 7.0 core) — the in-core prompt/model client features call.
- **AI Request Logs** — observability (the dominant recent theme).
- **MCP** adapters — expose abilities to external agents.
- ~~**`AI_Service`** layer~~ — **deprecated, and the card is closed.** Introduced in 0.2.1 (#101) as shared internal routing that experiments would migrate onto (#233), it was never adopted. PR [#905](https://github.com/WordPress/ai/pull/905) **merged 2026-08-11**: the class and the `get_ai_service()` helper stay, marked deprecated, after dkotter noted both are public surface a third party could be calling. **#233 closed against it**, closing out the last window's only "board contradicted by its own implementation" case. All experiments call `wp_ai_client_prompt()` directly.

Every roadmap item is a **new Experiment**, an **enhancement to one**, or **infrastructure/governance** beneath them.

## 4. Shipped (Done)

**v1.3.0 shipped on 2026-08-18 at 21:04 UTC — the 19th release, and the first thing this document has been able to record as *actually tagged* since 2026-07-14.** Board-Done moved **214 → 218**, and the release lane closed at 19/19.

### What v1.3.0 contains

The release notes credit four new Experiments and a substantial infrastructure layer:

- **Content Translation** (#747) — Paragraph/Heading blocks and optionally the post title, translated in the editor.
- **Slug Generation** (#897, #932) — SEO-friendly permalink suggestions.
- **Custom Abilities** (#881) — the standalone-ability opt-in gate from #863: `ai/get-post-details`, `ai/get-post-terms`, `core/read-settings`, `core/read-users`, `core/read-content` now require the experiment be enabled. **A behavior break for anyone already calling them.**
- **Import/Export of non-sensitive AI settings** and **AI-specific Site Health tests** (#734), **uninstall data cleanup** (#692), **prompt-template extension points** (#770), the public **`WordPress\AI\log_ai_request()`** API (#914), the `wpai_` meta-key rename with migration (#867), and refreshed default models (#913).

**⚠️ The embedding entry shipped anyway, reworded.** PR #946 — which switched off #892's `SDK_Overlay` on 2026-08-17 — asked that #892's changelog line be kept out of the release. The published notes instead **keep the entry and credit both PRs**: *"Brought the embedding code over from the PHP AI Client and load that conditionally so those using the AI plugin can start to take advantage of embedding generation (#892, #946)."* In `develop` the overlay does not load and `generate_embeddings()` returns `WP_Error`. A user reading the 1.3.0 notes will conclude the capability is available; it is not, and the follow-up tracker **#962** filed two days later is the board's acknowledgement of that.

### The three cards that reached Done

- **#924 Release version 1.3.0** — closed 2026-08-18 20:19 UTC, the checklist executed end to end: release PR #958 merged, plugin check and tests green, local testing, GitHub release, WordPress.org deploy, [make.wordpress.org announcement](https://make.wordpress.org/ai/2026/08/18/whats-new-in-ai-1-3-0/) at 22:32. A contributor had spotted the target-date typo on the ticket a week earlier; the target held at 2026-08-17 and slipped by one day.
- **#917 Content Resizing: focus the Accept button** — Infinite-Null's PR merged 2026-08-21 after 15 days open. A real contributor PR clearing review.
- **#940 Custom settings endpoint vs `/wp/v2/settings`** — closed 2026-08-19 by **uncarded** PR **#947** (hbhalodia), which raises the PUT/POST timeout rather than adding the custom endpoint the issue proposed. The card was also given milestone 1.4.0 on closure. **The board records a Done; it does not record that the shipped remedy is not the one specified.**

Four PR cards were added already-merged: **#941** (translation retry — uncarded for two windows, then carded on merge), **#948** (`core/read-users` ordered by display name, split out of #931), **#960** (1.3.0 screenshots), and #917 above.

### What did *not* get a card

The dependabot PRs were carded in previous windows and are not now, so even the routine lane has stopped being consistent. **The board contains no artifact of the release having been cut** other than #924's status flipping to Done.

### Board removals

**#193** (developer-only log panel) and **#869** (`window.aiProviderData` iframe-only false positives) were de-carded — both long closed. #193 is the notable one: it was *added* to the board on 2026-08-14 under milestone 1.0.0 and removed nine days later, a full add/remove cycle inside two refresh windows with no state change in between.

The durable shipped foundation remains:

- Toggleable experiments over shared Connectors and the WordPress AI Client.
- Abilities Explorer and an expanding set of read/manage abilities, now behind the Custom Abilities opt-in.
- MCP integration and request-log observability, with a public logging API.
- Type Ahead, Suggest Reply, Content Classification, generation, summarization, translation, slug suggestions, and editorial workflows.
- Repeated accessibility, internationalization, lifecycle, and provider-approval hardening.

## 8. Strategic read & risks

**Where it is heading:** discrete AI helpers are becoming a governed, agent-capable WordPress platform. Abilities provide the action primitive; Connectors and model preferences provide provider independence; editorial experiments provide user-facing workflows; search/RAG, MCP/WebMCP, and site-agent ideas connect those layers. v1.3.0 is the first release to ship a *gate* alongside the capabilities — the Custom Abilities toggle — which is the platform thesis arriving in a user-visible form.

**Watch-items / risks:**

1. **External dependencies — still the binding constraint, and now measurable in days.** `php-ai-client#274` has been the gate on re-enabling the plugin's embedding layer since 2026-08-17. It is still open, still BLOCKED, still `REVIEW_REQUIRED`, six days on, and #962's very first checklist item depends on it. The migration cost is now known rather than assumed: #274 removes `usingProvider()`/`usingModelPreference()` from `EmbeddingBuilder`, and `generate_embeddings()` plus the #891/#943 callers use both — so the follow-up to #946 is a caller rewrite, not a revert. Gutenberg remains the other lever: #949 is a direct port of `lib/experimental/knowledge` and `routes/guidelines`, tracked upstream as `gutenberg#77230`.
2. **Governance is arriving out of order — the code is landing ahead of the decision.** #863's toggle shipped in 1.3.0, and it shipped as a **breaking change** for anyone already calling `ai/get-post-details`, `ai/get-post-terms`, `core/read-settings`, `core/read-users`, or `core/read-content`. Meanwhile #923 (agent identity) is still In discussion under Future Release while **#961 implements it uncarded**, and #40 (Core Abilities) is still in Triage while its write half (#945) is in review. The pattern to watch is not "governance before write abilities" any more; it is that the board's decision cards keep trailing their own implementations.
3. **The release risk resolved; the scope risk moved one lane right.** 1.3.0 shipped one day late after 35 days, closing at 19/19 by **deferring #421** rather than finishing it. What replaces it is a 24-card 1.4.0 whose ten PRs are all BLOCKED or DIRTY with no approving review, plus an empty 1.5.0 created on release night. The absence of a 1.4.0 release issue is not itself a signal — trackers here are filed days before the release, not after the prior one — but the absence of a date *anywhere* on a lane that just absorbed a punt is. The pattern to watch is #421's: an item deferred to close a milestone, arriving in the next lane no readier than it left.
4. **Compatibility regressions** — **#933** (speech/image-only connectors falsely reported invalid) is review-ready and stalled; **#940** (settings saves wiping stored keys) closed against a timeout increase rather than the proposed bypass endpoint, so the core defect (`core.trac#65867`) is mitigated, not routed around. Upstream, `mcp-adapter#297` and `#298` are both fail-open/error-fidelity defects in the abilities-to-MCP bridge the plugin depends on.
5. **Board ≠ repo — the measurement itself is the problem now.** 30 open PRs = 18 direct + 11 linked + **1 unexplained**, the best open-PR coverage this document has recorded. In the same window **nine of thirteen merges were uncarded**, including the release PR and the PR that closed a board issue. A point-in-time audit of the *open* queue cannot distinguish "carded" from "shipped before anyone looked", and this window it scored a release as an improvement. If a coverage number is going to be used as a health signal, it needs a merged-PR arm.
6. **Board status is not delivery status** — #484 is non-Done though merged; #621 and #922 are Done though closed unmerged; #307 reached Done by being **declined**; **#892 is Done while its code is switched off**; **#940 is Done against a fix that is not the one it specified**; and **`php-ai-client#242` is In progress while closed upstream for five weeks**. Six distinct ways for a board state to mean something other than what it says.
7. **Board totals are not scope** — the total moved 279 → 291, but eleven of the fourteen additions were filed inside the window and only three cards reached Done. Growth here measures intake, not delivery; the release it contains is invisible in the count.
8. **Review throughput moved, and the standing queue did not.** Thirteen merges — the most in any window this document covers — every one merged by a maintainer, and only two of them contributor PRs that had been waiting (#917 at 15 days, #941 at 7). The open queue is unchanged: **0 of 30** with an approving review, an eleventh consecutive window at zero, **19 BLOCKED**, **17 failing checks**, 10 CHANGES_REQUESTED. Two green readiness moves (#459, #749) against two red (#887, #888) is the first non-monotonic window in months, but #935 — green checks, no requested changes, review-ready since 2026-08-19 — is the clean test case, and it is still sitting there. **#929 became the second on the window's last day**, leaving draft at 14:48 UTC with green checks and 2,907 added lines behind it.

## 10. How to refresh this document

> ⚙️ **Automated path:** [`wp-ai-roadmap-refresh.sh`](./wp-ai-roadmap-refresh.sh) does everything below in one command — re-pulls the board, diffs against the last snapshot (added / newly-Done / merged / status & milestone moves / removed), fetches the full PR/release census for all repositories declared through [`wp-ai-roadmap-repositories.json`](./wp-ai-roadmap-repositories.json), refreshes the curated dependency watchlist, and can append a changelog row (`--update-changelog`). Run with no args for a read-only report; add `--save` to roll all board, repository, release, and dependency baselines forward. The manual recipe below is what it automates.
>
> **Normal vs. strict refresh.** The default (normal) refresh is *warning-only*: any data-quality or coverage problem — an unreachable dependency, a substantive open PR with no board representation — is reported in the output (`.validation` in JSON, stderr lines otherwise) but never blocks the board report, and the run exits `0`. `./wp-ai-roadmap-refresh.sh --strict [--json]` runs the same read-only pipeline as an **audit**: it emits the complete report first, then exits `2` when any validation error remains (exit `1` is reserved for operational failures that prevented a report at all). A strict failure also suppresses `--save` and `--update-changelog` ("persistence skipped"), so a red audit never rolls the baseline forward.
>
> Strict is a **scheduled visibility audit, not a merge gate**: whether every substantive `WordPress/ai` PR is linked to Project #240 depends on upstream contributor behavior, so a persistent red result means *unresolved roadmap visibility* (work in flight that the board doesn't show), not a broken tracker. Point-in-time coverage: **30 open PRs** = 18 direct board PR cards + 11 linked to board issues (**all 11 via authoritative `closing` references**) + 0 routine dependency PRs + 0 linked-off-board + **1 unexplained (#961)** — one strict-audit failure, the best reading this document has recorded. Exactly one fallback-parsed relationship remains anywhere in the census: #494 → #238, on a direct board PR card. **Read that number with its blind spot in view.** It counts only PRs that are still open, and it improved partly because uncarded work *merged*: nine of the thirteen PRs that merged this window had no board card, including release PR #958 and #947, which closed board issue #940. A window in which the tracker misses a release will score better here than one in which the same work sits waiting. The issue-side audit has no such gap — every open `WordPress/ai` issue is checked against the board on every run (**52 of 52 carded**).
>
> **Cold-query caveat, now handled by the script.** GitHub computes PR mergeability lazily, so a first census can answer `mergeStateStatus: "UNKNOWN"` for PRs nothing has touched — the 2026-08-10 run reported 27 of 36 that way. `fetch_pr_census()` now re-asks once and keeps whichever answer knows more, warns (`pr-mergestate-unknown`, never an error) if any PR stays cold, and the PR diff ignores transitions into or out of `UNKNOWN`. Without that, one cold run reports every open PR as newly unreadable *and* persists the sentinel into the baseline, so the next window reports them all again in reverse.

**Prerequisite:** a `gh` login whose token has the `read:project` scope (fine-grained PATs scoped to a personal account **cannot** read the WordPress org project — even though it's public; use a classic-token login):

```bash
gh auth refresh -h github.com -s read:project
```

**1. Pull the full board** (paginated GraphQL → raw JSON). Save this query as `proj240.graphql`:

```graphql
query($org: String!, $number: Int!, $endCursor: String) {
  organization(login: $org) {
    projectV2(number: $number) {
      title shortDescription url
      items(first: 100, after: $endCursor) {
        totalCount pageInfo { hasNextPage endCursor }
        nodes {
          type
          fieldValues(first: 25) { nodes { __typename
            ... on ProjectV2ItemFieldSingleSelectValue { name field { ... on ProjectV2FieldCommon { name } } }
            ... on ProjectV2ItemFieldTextValue   { text field { ... on ProjectV2FieldCommon { name } } }
            ... on ProjectV2ItemFieldDateValue   { date field { ... on ProjectV2FieldCommon { name } } }
            ... on ProjectV2ItemFieldNumberValue { number field { ... on ProjectV2FieldCommon { name } } }
            ... on ProjectV2ItemFieldIterationValue { title startDate field { ... on ProjectV2FieldCommon { name } } } } }
          content { __typename
            ... on Issue { number title url state stateReason repository { nameWithOwner }
              labels(first:20){nodes{name}} assignees(first:10){nodes{login}} milestone{title}
              createdAt updatedAt closedAt comments{totalCount} }
            ... on PullRequest { number title url state isDraft repository { nameWithOwner }
              labels(first:20){nodes{name}} assignees(first:10){nodes{login}} milestone{title}
              createdAt updatedAt closedAt mergedAt }
            ... on DraftIssue { title assignees(first:10){nodes{login}} } } } } } } }
```

```bash
gh api graphql --paginate -f query="$(cat proj240.graphql)" -F org=WordPress -F number=240 > proj240_raw.json
```

**2. Normalize to flat items** (flattens custom fields into a `fields` object):

```bash
jq -s '[ .[].data.organization.projectV2.items.nodes[] ] | map({
  type:.type, itype:.content.__typename, number:.content.number, title:.content.title,
  url:.content.url, repo:.content.repository.nameWithOwner, state:.content.state,
  mergedAt:.content.mergedAt, milestone:.content.milestone.title,
  labels:[.content.labels.nodes[]?.name], assignees:[.content.assignees.nodes[]?.login],
  fields:( [ .fieldValues.nodes[] | select(.field.name!=null) |
    {key:.field.name, value:(.text // .name // (.date|tostring) // (.number|tostring) // .title)} ] | from_entries ) })' \
  proj240_raw.json > proj240_items.json
```

**3. Re-derive the key views:**

```bash
# Status distribution
jq -r 'group_by(.fields.Status)[] | "\(length)\t\(.[0].fields.Status)"' proj240_items.json
# All open issues (the roadmap), by status + milestone
jq -r '[.[]|select(.itype=="Issue" and .fields.Status!="Done")] | sort_by(.fields.Status,(.number)) | .[] |
  "[\(.fields.Status)] \(.milestone//"—") #\(.number) \(.title)"' proj240_items.json
# Milestone × Done/Open
jq -r 'group_by(.milestone)[] | "\(.[0].milestone//"(none)")\tTot:\(length)\tDone:\([.[]|select(.fields.Status=="Done")]|length)"' proj240_items.json
```

When refreshing: update the **Data snapshot** date in the header, re-check the §2 milestone table and §9 tracker, and add a §11 changelog entry.
