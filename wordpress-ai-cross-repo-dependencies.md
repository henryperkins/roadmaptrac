The dependency section intentionally tracks a **curated watchlist**, not every open Gutenberg or abilities-api issue. Gutenberg is too broad for whole-repo tracking to be useful here; the watchlist follows only items explicitly referenced by the WordPress AI roadmap, issue dossiers, or planned-work risk notes. The PHP AI Client, MCP Adapter, and Abilities API are narrower foundational repositories, so they receive a separate **full open-PR/issue/release census** without importing their issue backlogs as dossiers or imposing Project #240 coverage rules.

Watchlist **membership lives in `wp-ai-roadmap-dependencies.json`**, not in shell code. Each registry item declares `id` (`owner/repo#number`), `theme`, `aiRefs` (the WordPress AI issue numbers it affects, stored as integers), `note`, and `required`. Adding or removing a dependency is a reviewable JSON data change; the schema is validated on every run (`schemaVersion` 1, unique IDs, positive-integer `aiRefs`).

## Why This Exists

Project #240 is still the canonical source for `WordPress/ai` roadmap counts. The cross-repo watchlist captures upstream blockers and enabling work that can change the delivery path without changing Project #240:

- **Gutenberg**: Abilities and workflows, Guidelines/Skills, Media Editor, focal-point/media APIs, DataViews/admin UX, snackbar/toast accessibility.
- **abilities-api**: ability filtering, safety metadata, post-type CRUD abilities, core abilities scope, and ability meta.

### ⚠️ `abilities-api` is a graveyard, and the census is how you can tell

Adding this repository was expected to surface active keystone work. It surfaced the opposite, which is more useful.

**The Abilities API shipped into WordPress Core (PHP) and Gutenberg (JavaScript) and landed in Core for 7.0, so this standalone repository has served its purpose.** Issue [**#160** "Should this repository be archived?"](https://github.com/WordPress/abilities-api/issues/160) (jonathanbossenger, 2026-01-29) drew unanimous maintainer agreement — justlevine "a very strong **yes**", Jameswlepage "I don't see any reason to keep this open anymore… it has served its purpose", jeffpaul concurring and asking dd32/desrosj to perform the archival on 2026-02-04. **Nearly seven months later it is still open and the repository is still live.**

That single issue explains the whole shape of the census: **no open PR here has been touched since 2026-01-21**, the eight open issues are mostly proposals from late 2025, and the last non-prerelease was v0.4.0 in October 2025. The 14 open PRs are not a backlog anyone intends to review — several (#85 `wp_query_abilities`, #115/#119 ability filtering, #150 input/output validation filters) speak directly to open roadmap questions (`WordPress/ai` #21, #354, #348) but are stranded in a repository awaiting deletion.

**Consequence for this document:** treat abilities-api numbers as *archaeology*, not as in-flight work. Real Abilities API development now happens in `wordpress-develop` and `gutenberg`, neither of which is censused here — `gutenberg` deliberately (too broad to be a useful signal), `wordpress-develop` not at all. The curated watchlist below remains the only tracking of Abilities work that still matters, and it is watching a repository that is itself frozen.

## Refresh Notes

Run the normal refresh to include this watchlist in the JSON/Markdown report:

```bash
./wp-ai-roadmap-refresh.sh
```

Run the dependency-only path when you only need the cross-repo state:

```bash
./wp-ai-roadmap-refresh.sh dependencies
./wp-ai-roadmap-refresh.sh dependencies --json
./wp-ai-roadmap-refresh.sh dependencies --strict --json   # audit mode
```

Run the repository-only path for all four full PR/issue/release censuses:

```bash
./wp-ai-roadmap-refresh.sh census
./wp-ai-roadmap-refresh.sh census --strict
./wp-ai-roadmap-refresh.sh issuediff A.json B.json   # offline issue diff
```

Use `--save` on the normal refresh to persist the dependency snapshot plus independent `prs-<owner>-<repo>-*.json`, `issues-<owner>-<repo>-*.json`, and `releases-<owner>-<repo>-*.json` baselines for every available repository, so later runs can report state, readiness, issue, and release changes. A full `--save` now writes **14** files: `proj240` + (`prs`, `issues`, `releases`) × 4 repositories + the dependency snapshot.

The issue census is independently fail-soft. A failed issue fetch sets `issues_available: false`, records an `issue-census-unavailable` error, and leaves that repository's PR and release data intact — and it **skips the issue snapshot** rather than writing an empty array over a good baseline, which would otherwise report every issue as closed on the next run.

### Fetch behavior, UNKNOWN placeholders, and strict mode

- Every registry item is attempted on every run. A failed GitHub request for a **required** item is retried exactly once (two attempts total); **optional** items get one attempt.
- An unreachable item never disappears from the report. It is emitted as a placeholder with `state: "UNKNOWN"`, its configured theme/refs/note, and a structured `fetchError` (`{code, endpoint, attempts, message}`). The dependency diff therefore reports a temporary outage as a state change to `UNKNOWN`, not as a removed dependency — registry removal is the only thing that removes an item.
- The JSON result carries `validation` (`{ok, errors, warnings}`): a required `UNKNOWN` item is an error, an optional `UNKNOWN` item is a warning, and an invalid registry produces `dependency-registry-invalid` errors with an empty item list.
- Normal mode is warning-only and always exits `0` when a report was produced. `dependencies --strict --json` emits the same JSON first and then exits `2` when any validation error exists (exit `1` is an operational failure, e.g. an unreadable registry file).
- `aiRefs` are stored as integers in the registry and new snapshots; historical snapshots with `"#NNN"` strings remain readable, and renderers always print exactly one `#` prefix either way.
